# Computer System v0.1.0-alpha.10

This tenth public alpha gives CS-Linux a way to say that a program uses no OS
service and run it on the managed companion's compute plane, then deletes the
Rust/WebAssembly CS486 batch executor that the previous alpha had introduced,
because the measured speedup came from the compute worker and not from wasm. It
also repairs the CS-Linux login boundary, the in-world prompt cursor, the OS
runtime journal, guest wakeup ownership, and the Web Terminal's manual
connection-code entry.

This remains a prerelease. Back up a stopped world before testing it; persisted
data compatibility is not guaranteed between development alphas.

## Highlights

- Added `run --batch` to CS-Linux (Issue #114). It is a guest declaration, not
  an engine selection: the program promises to use no terminal, keyboard, clock,
  or filesystem service, and a batch process that reaches for one fails with an
  explicit `UnsupportedOperationError` rather than being approximated. A batch
  process may reach only `exit`, `heapInfo`, and `fsWrite` on fd 1 and fd 2, and
  that isolated CS ABI subset is served by the same handler in
  `src/application/runtime/csAbi.ts` that the in-session path uses, so the two
  cannot drift. `run --batch` is refused on DOS, in a pipeline or redirect, on a
  system utility, and on the queued MCP debug path. Where such a process runs is
  still operator configuration: with no compute plane it executes locally under
  the same isolated policy, which is not a fallback.
- Removed the Rust WebAssembly CS486 batch executor (Issue #115), so
  `Cs486Process` is once again the single production CS486 implementation. The
  real-BDS A/B taken for #114 ran with `WEB_COMPANION_CPU_ENGINE=typescript` and
  finished `run --batch --stats /tmp/b` in 498 ms of host wall time against
  2,332 ms without `--batch`. That 4.7x came from moving the program off the
  per-tick host admission path onto a compute worker, with the TypeScript
  interpreter doing the work. The wasm-only remainder could never reach an
  interactive or service-using program, since a worker owns no guest filesystem,
  terminal, scheduler, or DAC credentials, and widening it meant either a second
  source of truth for `ComputerRecord` state or a per-syscall host round trip.
  In exchange the repository was paying a permanent dual-implementation tax on
  every change to instruction semantics, cycle costs, and syscall policy.
- Deleted with it: the `wasm/` Rust crate and its toolchain pin, the wasm build,
  benchmark, and equivalence tooling with their `package.json` scripts, the
  `wasm-rust` engine value and the worker create protocol's `wasmModuleBytes`
  field, and the in-engine `WebAssembly` probe. The 2026-07-24 finding that the
  Bedrock Script API exposes no `WebAssembly` global survives as dated evidence
  in `docs/feasibility-matrix.md`. Compute workers, the remote `CpuProcess`
  protocol, the engine-selection seam, and the batch corpus all stay.
- Narrowed `WEB_COMPANION_CPU_ENGINE`, `--cpu-engine`, and the persisted
  `cpuEngine` field to the single value `typescript`. Any other value is
  rejected at configuration time, before a listener, a worker pool, or BDS
  exists, and the rejection now names the offending value bounded to 40
  characters instead of only listing what is allowed.
- Cleared the CS-Linux tty at the login boundary and re-armed released-terminal
  input (Issue #111). A prompt cursor now has exactly two owners: the screens
  that stop it (CSBIOS POST, the halt screens, the fail-stop state) and one
  restorer, `writeTerminalPrompt`, reached from every interactive prompt path
  including login and the masked password prompt. A booted Computer previously
  showed no cursor cell at its CS-Linux or CS-DOS prompt on the in-world
  display, and a guest that hid the cursor and exited left it hidden for the
  shell.
- Made a failed boot readable and bounded the OS runtime journal (Issue #112).
  The journal rotates rather than growing, and a CSBIOS boot failure is visible
  on the screen instead of leaving a blank terminal.
- Gave `terminal_keys` one wakeup owner and bounded atomic CPU sub-slices (Issue
  #113). A 66 MHz CS486DX2 tick budget of 3,300,000 modeled cycles is split into
  ten 330,000-cycle sub-slices, and cumulative CPU accounting no longer
  saturates.
- Fixed manual connection-code entry in the Web Terminal. The permanent
  four-digit number names both an unconsumed activation and the session that
  already owns it, but the dialog implemented only the one-use half, so a
  browser holding no token dead-ended on "A valid browser terminal token is
  required." even inside the 3-block range. Manual entry now falls through 401
  and 410 into the existing bounded reconnect exchange, which already owns range
  waiting, backoff with jitter, the attempt and lifetime caps, and `Retry-After`
  handling.

## Install

1. Back up the stopped target world.
2. Download and open `computer-system-0.1.0-alpha.10.mcaddon`.
3. Activate the imported Computer System Behavior Pack; its dependency activates
   the matching Resource Pack.
4. Use Minecraft Bedrock Edition 1.26.30 or later in the 1.26 release line.

The release ships Resource Pack 0.1.18 and Behavior Pack 0.1.14. Separate
Behavior and Resource `.mcpack` files and `SHA256SUMS.txt` are provided for
independent verification and import.

Live Web Terminal features require the source release and the local companion;
GitHub Pages remains documentation only. Compute workers are an operator-run
mode of that same local companion and are not part of the installed packs.

## Alpha boundaries

- `run --batch` is not a general accelerator. It helps a computation-bound
  program that needs no OS service. Interactive programs such as NetHack, `vi`,
  and the Python REPL are paced by the 20 TPS scheduler tick and by key input,
  so they cannot benefit; `run --batch /usr/games/nethack` correctly fails with
  `UnsupportedOperationError: batch process cannot use CS ABI operation 5`.
- Modeled guest evidence is unchanged by where a process runs. In the acceptance
  measurement the batch and non-batch runs of the same executable agreed exactly
  on instructions, CPU cycles, L1/L2 hits and misses, bus transfers, unaligned
  accesses, and pipeline flushes; only host wall time differed. Host wall time
  on a guest statistics line is responsiveness, not guest speed.
- Hosted CS-Linux stdout can still be silently truncated inside a tick on the
  non-batch path. `src/application/runtime/csAbi.ts` answers a deferred
  `terminal` lane with `EAGAIN` instead of suspending through `wait_event`, and
  guest libc does not retry. This is a pre-existing defect, unrelated to the
  wasm removal, reproduced unchanged in the acceptance run and recorded in
  `docs/issues/issue-115-remove-wasm-executor.md`. It needs its own Issue.
- The managed runtime-worker build still requires the irreversible Beta APIs
  experiment for its private loopback transport. It never enables that
  experiment silently on a preserved world; stop BDS, make a full world backup,
  and obtain explicit operator consent first. Only a newly generated disposable
  acceptance world beneath the current user's temporary directory is enabled
  automatically.
- Guest execution inside Bedrock itself remains the TypeScript interpreter in
  the Script API engine. Native DLL, hypervisor, and in-engine wasm execution
  remain not Bedrock-compatible paths.
- Issue #16's multi-user load evidence still does not exist. Sequential success
  is not multi-user capacity proof.
- This is not the project's Phase 6 release-hardening milestone, and it is not
  long-duration multiplayer acceptance.
- Persisted world/data compatibility is not guaranteed between development
  alphas.
- Guest networking, package management, dynamic loading, unrestricted
  processes/threads/sockets, and CS Windows remain future work.
- The preserved reduced NetHack prototype remains excluded from release
  completion percentages.

## Verification

- `npm run validate` passed formatting, ESLint, TypeScript, 311 Vitest files
  with 2,596 tests, the hosted-C and generated NetHack payload checks, the
  production Bedrock pack build, and the 16-chapter Pages build.
- Real-BDS acceptance for `run --batch` on a disposable
  `ComputerSystemAcceptance` world with two compute workers and the `typescript`
  engine, before the wasm removal: `run --batch --stats /tmp/b` returned
  `498.000 ms` against `2332.000 ms` for the same executable without `--batch`.
- The same acceptance repeated after the removal on an isolated fixture returned
  `513.000 ms`, the same range, with every modeled counter identical between the
  batch and non-batch runs. A second fixture whose program printed nothing
  recorded 1,400,054 instructions on both paths, 443 ms batch against 2,433 ms
  and 2,427 ms non-batch.
- Real-BDS evidence for the #111 cursor work: with the MCP debug writer
  registered on a placed Computer at its CS-Linux login prompt, the validated
  text surface reports `cursor.blink === true` with the cursor in the cell after
  the prompt's trailing space; the same read on the previous build reported
  `false`. The in-world Bedrock CRT look at the block face remains outstanding
  and is recorded as such.
- Real-BDS evidence for #113: over 9,320 completed ticks on a CS486DX2 fixture
  the largest atomic `guest_cpu` host operation stayed bounded by the ten-way
  sub-slice split.
- The exact `Verify:` and `Expect:` steps are recorded in
  `docs/issues/issue-114-run-batch-cs-abi.md`,
  `docs/issues/issue-115-remove-wasm-executor.md`, and the #111/#112/#113 issue
  documents.

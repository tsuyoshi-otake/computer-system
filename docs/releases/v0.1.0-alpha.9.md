# Computer System v0.1.0-alpha.9

This ninth public alpha turns the Rust/WebAssembly CS486 batch executor measured
in the previous alpha into a selectable engine for the managed companion's
compute workers, extends the same compute plane to MCP debug sessions so an
MCP-driven verification actually executes on the engine it names, deletes the
rejected AssemblyScript prototype variant, and corrects CS386SX memory cost and
floating-point syscall behavior.

This remains a prerelease. Back up a stopped world before testing it; persisted
data compatibility is not guaranteed between development alphas.

## Highlights

- Made the Rust WebAssembly batch executor an operator-selectable engine for the
  managed companion's compute workers. `WEB_COMPANION_CPU_ENGINE` and the
  persisted `cpuEngine` admin-config field accept `typescript` (the default) and
  `wasm-rust`. One `Cs486ComputeCpuEngine` contract is the only place the two
  implementations are told apart, so the worker entry, the pool, and the
  loopback wire protocol stay engine-agnostic. The admin config moved to version
  3 with a key-introduction table so an older companion cannot silently ignore a
  newer key.
- Made a selected wasm engine's artifact mandatory rather than best-effort. When
  `wasm-rust` is selected the pool resolves
  `wasm/dist/cs486-batch-executor.rust.wasm` before spawning any worker, and a
  missing or malformed artifact rejects pool initialization and therefore fails
  managed startup explicitly. There is no implicit fallback to the TypeScript
  engine, because a silent fallback would attribute guest results to an engine
  nobody selected. The default `typescript` engine resolves no artifact. Each
  worker reports the engine it actually loaded and a mismatch is a protocol
  failure, so a thread that loaded something else never becomes ready.
- Extended the same compute plane to the MCP debug companion.
  `BDS_MCP_RUNTIME_WORKERS` unset or `0` keeps the in-engine CPU and starts no
  threads and no listener; `1` through `16` opts in; anything else is a startup
  `RangeError`. Selecting a non-default engine while the workers stay disabled
  is rejected before the world is touched. `bds_status` reports the worker count
  and endpoint, the selected `cpuEngine`, and the compute listener/pool
  snapshot, and the plane's bearer token never enters a tool result.
- Deleted the AssemblyScript batch-executor variant and its engine entry, and
  narrowed the wasm variant and benchmark engine lists to the Rust variant.
  AssemblyScript failed the project's ≥2x median host-cost adoption gate in the
  previous alpha, so it had no remaining role; its measurements stay in the
  issue document as the record that decided it. Rust is now the only maintained
  wasm variant.
- Recorded that the CS486 contract now has two production implementations. A
  change to a responsibility they share must land in `Cs486Process` and in the
  wasm batch executor in the same change, and
  `npm run verify:cs486-wasm-equivalence` is the named agreement proof.
- Corrected CS386SX cost and fault fidelity (Issue #110). Every `cs.fp.*`
  syscall now faults on CS386SX at dispatch, matching an 80386SX's dependency on
  a discrete 80387SX that Portable computers do not model; CS486DX/DX2 keep
  executing FP syscalls at their documented cost. The data-access cost formula
  no longer gives an even-aligned dword access a free ride, so CS386SX pays the
  full per-transfer main-memory cost on every load, store, push, pop, and
  syscall word transfer, while CS486DX/DX2 pay that same per-transfer rate only
  on an L1/L2 cache miss. Modeled cycle counts therefore change for
  memory-touching guest programs; the wasm batch executor's cost formula was
  ported in the same change so differential equivalence holds.
- Fixed `npm run build:cs486-wasm` to spawn its toolchain without `shell: true`,
  which matters now that an operator selecting `wasm-rust` must build the
  artifact, and documented in `docs/development.md` how to obtain the official
  BDS distribution.

## Install

1. Back up the stopped target world.
2. Download and open `computer-system-0.1.0-alpha.9.mcaddon`.
3. Activate the imported Computer System Behavior Pack; its dependency activates
   the matching Resource Pack.
4. Use Minecraft Bedrock Edition 1.26.30 or later in the 1.26 release line.

The release ships Resource Pack 0.1.18 and Behavior Pack 0.1.13. Separate
Behavior and Resource `.mcpack` files and `SHA256SUMS.txt` are provided for
independent verification and import.

Live Web Terminal features require the source release and the local companion;
GitHub Pages remains documentation only. The compute-worker engine selection is
an operator-run mode of that same local companion and is not part of the
installed packs.

## Alpha boundaries

- `wasm-rust` remains opt-in and `typescript` remains the default engine. The
  real-BDS p95 tick non-regression comparison between the two engines has not
  been measured, and Issue #16's multi-user load evidence does not exist yet.
  Until both exist there is no basis for changing the default; a single-engine
  PASS is not a non-regression measurement.
- The Rust wasm artifact is not checked in. A source checkout that selects
  `wasm-rust` without running `npm run build:cs486-wasm` first fails managed
  startup explicitly rather than degrading to the interpreter. The default
  `typescript` engine needs no artifact and is unaffected.
- The managed runtime-worker build requires the irreversible Beta APIs
  experiment for its private server-admin/server-net loopback transport. It
  never enables that experiment silently on a preserved world; stop BDS, make a
  full world backup, and obtain explicit operator consent first. Only a newly
  generated disposable acceptance world beneath the current user's temporary
  directory is enabled automatically.
- The Bedrock Script API exposes no `WebAssembly` global, so any wasm benefit is
  scoped to the Node-side managed companion and never applies to guest execution
  running inside Bedrock itself. Native DLL and hypervisor execution remain not
  Bedrock-compatible paths.
- This is not the project's Phase 6 release-hardening milestone, which is
  numbered independently of Issue #106's internal phases, and it is not
  long-duration multiplayer acceptance.
- Modeled `cpuCycles` for memory-touching guest programs are not comparable with
  numbers recorded on v0.1.0-alpha.8 or earlier, because the corrected
  data-access cost formula changes them. Guest CPU identity, clock, and per-tick
  admission are unchanged.
- Persisted world/data compatibility is not guaranteed between development
  alphas.
- Guest networking, package management, dynamic loading, unrestricted
  processes/threads/sockets, and CS Windows remain future work.
- The preserved reduced NetHack prototype remains excluded from release
  completion percentages.

## Verification

- `npm run validate` passed formatting, ESLint, TypeScript, 310 Vitest files
  with 2,562 tests, the hosted-C and generated NetHack payload checks, the
  production Bedrock pack build, and the 16-chapter Pages build.
- A real-BDS MCP session on a disposable `ComputerSystemAcceptance` world with
  `BDS_MCP_RUNTIME_WORKERS=2` and `WEB_COMPANION_CPU_ENGINE=wasm-rust` confirmed
  the guest-side leg end to end. Both workers reported `cpuEngine` `wasm-rust`
  on a loopback compute listener, and a guest C program written, compiled, and
  run through `bds_execute_computer_command` on a provisioned CS486DX2 Computer
  printed `8386560` with exit code `0` and 233,531 instructions for 439,093
  modeled CPU cycles at 66 MHz, reported `halted`. The `bds_status` snapshot
  taken while that program was resident attributed `ownedProcessCount` `1` to a
  worker reporting `cpuEngine` `wasm-rust`, so the printed result came from a
  compute worker and not from the in-engine CPU. Diagnostics were empty and the
  session stopped to `idle`. The exact `Verify:` and `Expect:` steps are
  recorded in `docs/issues/issue-106-wasm-batch-executor.md`.
- Host wall time on a guest statistics line is MCP responsiveness, not guest
  speed, and that single-engine session is not a `typescript`-versus-`wasm-rust`
  comparison.
- The two production CS486 implementations are held in agreement by
  `npm run verify:cs486-wasm-equivalence`; the differential-equivalence results,
  the Phase 4 A/B matrix, the adoption-gate verdict, and the
  Rust-versus-AssemblyScript selection rationale remain recorded in
  `docs/issues/issue-106-wasm-batch-executor.md`.

# Computer System v0.1.0-alpha.11

This eleventh public alpha is a single-subject release: it makes the one
production CS486 implementation faster without changing anything it computes.
The interpreter's hot execution burst now covers memory and stack instructions
in addition to register and ALU ones, and it dispatches through instruction
lanes so that a simple instruction stops paying for the checks a complicated one
needs.

Nothing about the guest changed. Modeled cycles, cache statistics, registers,
guest RAM, program output, and every fault message are identical to
v0.1.0-alpha.10, and that identity is the acceptance evidence for the change
rather than a side note.

This remains a prerelease. Back up a stopped world before testing it; persisted
data compatibility is not guaranteed between development alphas.

## Highlights

- Extended `Cs486Process`'s hot execution burst to loads, stores, `push`, `pop`,
  `call`, and `ret` (Issue #116). Before this release the burst covered 21
  register, ALU, and control-transfer opcodes, so every memory or stack
  instruction left it and paid a full outer-loop round trip. That is why
  memory-shaped guest code ran at roughly half the throughput of ALU-shaped
  guest code.
- Made the burst take its side effects in exactly the order the cold path takes
  them: instruction fetch, then the control-transfer record, then the operation.
  That order was unobservable while the burst held only ALU instructions. It
  becomes observable the moment memory instructions join, because the
  instruction and data streams share one unified L1 on CS486DX/DX2, and their
  interleaving decides hit/miss classification, replacement, and every counter
  derived from them.
- Kept every fault owned by one implementation. An instruction that could fault
  is refused to the cold path _before_ its first modeled side effect, so
  `executeNext` re-executes it against an untouched modeled machine and remains
  the only place that raises a memory, alignment, stack, or instruction-target
  fault and words its message. The burst never invents an error text.
- Split dispatch into instruction lanes. A register or ALU instruction cannot
  fault, cannot transfer control, and has no address to admit, so it must not be
  charged for testing any of that. A first attempt that put every check in one
  flat switch measured 0.89x–0.92x on ALU-heavy code even while memory-heavy
  code improved; the lane split removed that cost and kept the gains.
- Removed the `Cs486Register` string switch from `push` and `pop`, which ran on
  every stack operation. ESP is addressed by its constant register index
  instead. The register file is `Int32Array`-backed, so the stored value is
  unchanged.

## Measured effect

Alternating A/B measurement over three interleaved rounds, 4,000,000
instructions and 9 samples per configuration, across the `alu-branch`,
`mem-stack`, and `hosted-c-mid` corpora and all three CPU profiles.
`hostInstructionsPerSecond` in millions, best of three rounds, before → after:

| corpus                 | CS386SX     | CS486DX   | CS486DX2  |
| ---------------------- | ----------- | --------- | --------- |
| alu-branch cpu-slice   | 105.7→144.3 | 98.1→94.5 | 95.3→94.2 |
| mem-stack cpu-slice    | 71.0→97.7   | 46.9→61.5 | 44.7→58.0 |
| hosted-c-mid cpu-slice | 79.0→126.9  | 59.2→83.5 | 60.7→82.9 |

Geometric mean across all 18 measured configurations is 1.132x. The gain lands
on `runCpuSlice`, which is the path the scheduler uses. `runInstructionSlice`
does not enter the burst and is flat, within ±2% in every configuration.
`hosted-c-mid`, the corpus closest to real guest C, gains 1.37x–1.61x.

One configuration is not a gain: purely ALU-and-branch code on CS486DX and
CS486DX2 measures 0.95x–0.99x across repeated runs, so it is flat to marginally
slower. That is the residual cost of the lane lookup on the one instruction
shape that needs nothing else, and it is stated here rather than averaged away.
Guest code that only computes in registers and never touches memory is not a
shape real programs hold for long.

Host throughput is host responsiveness. It is not guest speed, and it does not
change what a guest program observes about its own machine.

## Alpha boundaries

- This is a host-throughput change with no guest-visible effect by design. If a
  future change to the burst alters a modeled cycle, a cache counter, or a fault
  message, that is a defect in the change, not a new capability.
- Real-BDS `run --stats` before/after comparison for Issue #116 is not yet
  recorded. The host equivalence evidence covers what the guest computes; the
  in-world measurement of host wall time remains open and is listed as open in
  `docs/issues/issue-116-cs486-dispatch-structure.md`.
- Multiply, divide, modulo, indirect calls, `syscall`, `print`, and `halt` stay
  on the cold path deliberately. CS386SX prices multiply from the runtime
  multiplier, divide-by-zero is value-dependent, indirect calls need signature
  admission, and the rest reach process-level state.
- A separate attempt to inline `SetAssociativeCache`'s hit path and split its
  replacement hint was measured and reverted at 0.997x. It is recorded so it is
  not retried blind.
- Hosted CS-Linux stdout can still be silently truncated inside a tick on the
  non-batch path. `src/application/runtime/csAbi.ts` answers a deferred
  `terminal` lane with `EAGAIN` instead of suspending through `wait_event`, and
  guest libc does not retry. This pre-existing defect is unchanged by this
  release and still needs its own Issue.
- `Cs486Process` remains the single production CS486 implementation. This
  release adds no second interpreter, transpiler, or native executor, and
  generates no host code at runtime.
- Guest execution inside Bedrock itself remains the TypeScript interpreter in
  the Script API engine. Native DLL, hypervisor, and in-engine wasm execution
  remain not Bedrock-compatible paths.
- Issue #16's multi-user load evidence still does not exist. Sequential success
  is not multi-user capacity proof.
- This is not the project's Phase 6 release-hardening milestone, and it is not
  long-duration multiplayer acceptance.
- Guest networking, package management, dynamic loading, unrestricted
  processes/threads/sockets, and CS Windows remain future work.
- The preserved reduced NetHack prototype remains excluded from release
  completion percentages.

## Verification

- Equivalence: three interleaved A/B rounds compared `guestCycles`,
  `guestRamSha256`, `registerChecksum`, every architectural register,
  `instructionPointer`, `hasPendingCpuCycles`, guest output, and every
  microarchitecture counter — `instructionFetches`, `l1Hits`, `l1Misses`,
  `l2Hits`, `l2Misses`, `busTransfers`, `unalignedAccesses`, and
  `pipelineFlushes` — across CS386SX, CS486DX, and CS486DX2. No field differed
  in any of the 18 configurations.
- `npm run validate` passed formatting, ESLint, TypeScript, 311 Vitest files
  with 2,596 tests, the production Bedrock pack build, and the 16-chapter Pages
  build.
- The exact `Verify:` and `Expect:` steps are recorded in
  `docs/issues/issue-116-cs486-dispatch-structure.md`.
